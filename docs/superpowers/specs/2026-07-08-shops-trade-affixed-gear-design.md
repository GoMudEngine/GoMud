# Shops Trade Affixed Gear — Design Spec

**Date:** 2026-07-08
**Status:** Approved for staging (each stage gets its own implementation plan)
**Author:** Calabe Davis + Claude

## Problem

Instance-zone loot is generated by `items.GenerateAffixedItem` (`internal/items/
affixgen.go`): it spends a gold-derived point budget on random stat/mitigation/
damage/skill bonuses and stamps them onto a **per-instance spec copy**
(`item.Spec = &specCopy`). Two gaps make this loot economically invisible:

1. **Unsellable.** `Item.IsSpecial()` (`items.go:436`) returns `true` whenever
   `i.Spec != nil`. Affixed items always carry a per-instance `Spec`, so
   `Mob.GetSellPrice` (`mobs.go:894`) returns `0` — the item literally cannot be
   sold.
2. **Mispriced.** Even if sold, `GetSellPrice` reads `item.GetSpec().Value`,
   which for an affixed item is still the **base template value** — the affix
   bonuses (the whole point of instance loot) never raise it. A budget-30
   affix-boosted sword and a plain one price identically.

Downstream, mob equipment-shopping (`internal/itemvalue`) scores affix stat mods
for *swap* decisions, but shop **pricing** (`shops.CalcBuyPrice`/`CalcSellPrice`)
keys off `spec.Value`, so the two systems disagree about what affixed gear is
worth.

## Goals

- **Affixed gear carries a gold value that scales with its affix power**, and
  that value flows through the existing pricing path.
- **Players can sell affixed instance loot** for gold scaled to that value.
- **Shops buy affixed gear at a scaled price and resell it with a markup** — the
  exact affixed item, not a base substitute.
- Establish a reusable **gold-per-affix-point rubric** that later seeds a broader
  catalog value audit.

## Non-Goals

- **Do not weaken `IsSpecial()` globally.** It gates stacking and other paths
  beyond selling. The sell allowance for affixed items is explicit and
  affix-scoped.
- **Enchanted items stay out of scope** (they also set `i.Spec != nil` but are a
  separate system with `EnchantType`/`EnchantTier`). They remain unsellable as
  today unless a future decision folds them in.
- **No new interactive UX** beyond what sell/buy/list already show.
- **Stage 4 (catalog audit) is a separate follow-on project**, not built here.

## Design

### Core primitive — `items.AffixValue`

A pure function computing an affixed item's gold value from the diff between its
per-instance spec and the base template spec, using the affix cost table
(`affixgen.go` `allBonusTypes`) as the power-weighting:

```
AffixValue(spec, baseSpec) =
    baseSpec.Value
  + affixPoints(spec, baseSpec) * Balance.GoldPerAffixPoint

affixPoints(spec, baseSpec) =
    round((spec.DamageMultiplier      - baseSpec.DamageMultiplier)      / 0.05) * 8   // damage_mult_phys cost
  + round((spec.SpellDamageMultiplier - baseSpec.SpellDamageMultiplier) / 0.05) * 4   // the +spell half of damage_mult_both (12-8)
  + (spec.PhysicalMitigation   - baseSpec.PhysicalMitigation)   * 5
  + (spec.MagicalMitigation    - baseSpec.MagicalMitigation)    * 5
  + (spec.ConvictionMitigation - baseSpec.ConvictionMitigation) * 5
  + Σ over StatMods deltas: statDelta*3 (stats) or skillDelta*12 (skills)
```

Notes:
- Damage split: `damage_mult_phys` (cost 8) adds +0.05 phys; `damage_mult_both`
  (cost 12) adds +0.05 to both phys and spell. Weighting phys at 8/0.05 and
  spell at 4/0.05 reconstructs the correct point cost from the diff regardless of
  which affix produced it.
- Skill vs stat is disambiguated by `isSkillMod(name)` (already in `affixgen.go`).
- Only positive deltas count (affixes never subtract).
- Config: one new `Balance.GoldPerAffixPoint` (float). **Default 3.0**, chosen
  from the modeling below (see Calibration): GPP=2 was the conservative baseline;
  GPP=3 lands premium oasis gear ~50% higher, which matches the desired feel.

`GenerateAffixedItem` stamps `specCopy.Value = AffixValue(specCopy, baseSpec)`
after applying bonuses, so the per-instance `Value` is authoritative and every
downstream `spec.Value` reader (including `GetSellPrice`) sees the scaled value
with no further change.

### Affixed-item marker

To let the sell path allow affixed items **without** touching `IsSpecial` or
un-protecting enchanted items, mark affixed items explicitly at generation. The
sell path treats an item as affixed-sellable when this marker is set; all other
`i.Spec != nil` items (enchanted, uses-modified, blob) stay blocked as today.
(Exact field/mechanism chosen in the Stage 2 plan; candidates: a dedicated
`Item.Affixed bool`, or keying off the affix `Adjectives` prefix + absence of
`EnchantType`. The plan will pick the least-surprising option and lock it with a
test.)

### Pricing model for unique affixed items (fixed spread, NOT scarcity)

Modeling surfaced a hard constraint: the dynamic `ScarcityMultiplier`
(`shops/pricing.go`) can't price unique gear — a qty-1 affixed item always reads
"scarce" and the multiplier runs up toward the 5× ceiling. So affixed trades use
a **fixed spread off `AffixValue`**, bypassing the scarcity curve:

- **Player sell → shop:** `AffixValue × ShopBuyRatio` (0.5). This deliberately
  **overrides the legacy `Mob.GetSellPrice` 25% cap** for affixed items — they're
  premium instance rewards, priced on value, not the commodity 25% rule. (Stage 2
  routes affixed sells through this instead of the capped path, which also
  returns 0 for `IsSpecial`.)
- **Shop relist → player:** `AffixValue × 1.0` (full value). Shop margin is the
  half it underpaid on purchase.

### Calibration (from modeling, 2026-07-08)

Grounded in real values (`LootBudgetScalar` = 7.0, so `budget = floor(7×√buyIn)`;
Tidal Torc base 85, Earthshaker Warhammer base 80). Buy-in = gold paid to open
the instance.

| Item | Buy-in | budget | AffixValue @GPP=3 | Player sells (0.5×) | Relist (1.0×) |
|------|-------:|------:|------:|------:|------:|
| Tidal Torc | 200 | 98 | 379 | ~190 | ~379 |
| Tidal Torc | 300 | 121 | 448 | ~224 | ~448 |
| Earthshaker | 200 | 98 | 374 | ~187 | ~374 |
| Earthshaker | 300 | 121 | 443 | ~222 | ~443 |

Verdict (user, 2026-07-08): in the right ballpark, not orders of magnitude off.
GPP=3 (~50% above the GPP=2 baseline) is the chosen default. **Separately, the
base template values of premium items are too low** (an oasis torc at 85g / a
warhammer at 80g) — the **Stage 4 catalog audit should raise these base values**;
the affix model rides on top of whatever base we settle on.

### Staging

Each stage is independently shippable, leaves the game working, and gets its own
implementation plan. Stage 1 precedes all; 2 precedes 3; 4 is a separate project.

| Stage | Scope | Ships |
|-------|-------|-------|
| **1 — Value primitive** | `items.AffixValue` + `Balance.GoldPerAffixPoint`; stamp `Value` in `GenerateAffixedItem`. Pure + fully unit-tested. No sell/shop behavior change (items still `IsSpecial`-blocked). | Correct intrinsic value on affixed items; foundation for all pricing. |
| **2 — Sellability (melt)** | Explicit affixed marker; narrow sell-path allowance so affixed items sell for `AffixValue`-scaled gold. Item consumed on sale (no resale yet). Enchanted/other custom-spec items stay blocked. | Players can finally sell instance loot for fair gold. |
| **3 — Shop resale** | Extend `characters.ShopItem` to carry an optional per-instance `items.Item`; thread through `GetInstock`/listing/buy/pricing + shop YAML persistence. Sell → adds affixed item to stock at scaled buy price; buy → hands back the exact affixed item at `AffixValue × 1.0`. Uses the **fixed spread** (sell 0.5×, relist 1.0×), NOT `ScarcityMultiplier`. Clutter control: cap affixed entries per shop + make them temporary/decaying to respect the 20-variety limit. | Full "shops trade affixed gear" loop, surviving restart. |
| **4 — Catalog value audit** (separate project) | Apply the `GoldPerAffixPoint` rubric to audit/retune base `Value`s across the catalog — **starting with premium/instance items whose bases are too low** (oasis torc 85g, warhammer 80g). Spot mispriced items. | Consistent economy-wide item values. |

### Data flow

- **Generation:** `GenerateAffixedItem` → apply bonuses → `specCopy.Value =
  AffixValue(...)` + set affixed marker.
- **Sell (Stage 2):** sell command → affixed marker allows it → price from
  `GetSellPrice` (reads scaled `spec.Value`) → player credited, item removed.
- **Sell→stock (Stage 3):** the sold affixed `items.Item` is stored on a
  `ShopItem` (per-instance) at the fixed-spread buy price (`AffixValue × 0.5`).
- **Buy (Stage 3):** listing shows affixed stock entries; purchase clones the
  stored `items.Item` to the buyer at `AffixValue × 1.0`; entry decrements.
- **Persistence (Stage 3):** shop YAML serializes per-instance stock entries so
  affixed stock survives restart.

### Testing strategy

- **Stage 1:** table tests for `AffixValue` across affix combinations (stats,
  mitigations, damage phys/both, skills, mixed); assert `GenerateAffixedItem`
  stamps a `Value` strictly greater than base when budget > 0, equal when 0.
- **Stage 2:** affixed item is sellable and priced by `AffixValue`; enchanted /
  uses-modified / blob items remain unsellable (regression guard on `IsSpecial`
  behavior); the existing `mobs` sell-price tests stay green.
- **Stage 3:** sell→stock→buy round-trips the exact affixed spec; markup applied;
  YAML persistence round-trips an affixed stock entry; clutter cap enforced.

## Risks & Mitigations

- **Weakening item protection** → never change `IsSpecial`; use an explicit
  affixed marker with a regression test proving enchanted/blob items stay
  blocked.
- **Shop pricing pollution** (a sold affixed item mispricing base stock) →
  affixed stock is a distinct per-instance entry, never merged into the base
  `ItemId` stock line.
- **Shop clutter / 20-variety cap** → cap affixed entries per shop + temporary
  decaying stock; `log()`/document the cap so it isn't a silent truncation.
- **Persistence bloat** → per-instance stock entries add YAML weight; keep them
  temporary/decaying so they don't accumulate unbounded.
- **Value inflation** → `GoldPerAffixPoint` is a single tunable knob; start
  conservative and validate against base template values before prod.

## Out-of-Scope Follow-ups

- Enchanted-item sellability (same machinery could extend to it later).
- The broader catalog value audit (Stage 4) as its own spec → plan cycle.
