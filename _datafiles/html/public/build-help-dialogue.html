Dialogue Editor — Admin Guide

This page explains how NPC dialogue actually works in the game, what every section of the dialogue editor does, and walks one small quest-giver from empty file to working conversation. The editor refuses saves that break the house rules and warns about the rest — every refusal it can raise is listed at the bottom.

Edits are live the moment you save. No reboot: walk to the NPC in-game and talk to it to test what you just wrote.

1. How players reach dialogue

There are exactly three ways a player hears an NPC's dialogue:

SurfaceWhat fires
talk <npc> The tree's root text (or the first matching quest-gated root variant), plus its hints. An NPC with no tree falls back to a catch-all pattern; with neither, it just nods.
ask <npc> <topic> The real driver of conversation. Tree nodes are checked first (the topic is matched against node triggers, in file order), then patterns (topic matched against keywords). No match: the NPC shakes their head.
Walking into the room A greeting fires by itself — once per player per NPC per boot, at most one greeter per entry, skipped if the NPC is busy or the player is sneaking.
Other commands — say, whisper, emotes — do not reach this system. If a player types ask <npc> quest and nothing quest-shaped matches, the engine answers for the NPC: "I have no task for you right now." That is why every quest-granting node must carry quest and task in its triggers — it makes ask <npc> quest the universal "do you have work for me?" gesture.

2. The three sections of a dialogue file

Greetings — ambience, not conversation

Short one-liners the NPC says when a player arrives. Write several and the engine picks one that matches the NPC's current mood (a greeting with an empty mood list matches any mood). Greetings never carry quest logic — they are flavor only.

Patterns — a keyword FAQ

Each pattern is a bag of keywords and a pool of responses (one is picked at random). If the player's ask topic contains a keyword, the pattern fires. Patterns have no memory and no ordering between question and answer — they are the NPC's standing answers about the town, their trade, the weather. A pattern with a single empty-string keyword is the catch-all: it answers anything that matched nothing else.

The tree — actual conversation, and all quest logic

The tree is what makes a conversation rather than an FAQ:

  • Root — what the NPC says to talk. Its hints are the narrator telling the player what they could ask next.
  • Root variants — quest-gated replacements for the root, so the opener changes as the player's quest state changes. First match wins.
  • Nodes — the branches. A node fires when the ask topic contains one of its triggers — checked in the order the nodes are listed, which is why the editor shows them as an ordered list with ↑/↓ controls.

Two fields chain nodes into an arc: a node with Requires only fires after one of the named nodes has fired for that player, and Unlocks marks named nodes as reachable. Combined with hints, this yields the shape: root text points at a topic → the node for that topic points at the next topic → the last node grants the quest.

3. Moods, in one paragraph

Every NPC instance carries one current mood — friendly, neutral, hostile, afraid, or grateful — starting at the file's default mood. A greeting or pattern that lists moods only fires while the NPC is in one of them. A fired line's Mood change shifts the mood. That is the whole system. Most NPCs never need it: leave every mood list empty (= any mood) and ignore Mood change unless the NPC should answer differently after being pleased or provoked — e.g. a bribe pattern that sets mood to friendly, unlocking friendlier answers to the same questions.

4. Worked example — a small quest-giver

Miller Hobb has lost his donkey. Quest 41's start token is 41-start, its end token 41-end. Built in the editor:

Default mood: neutral. Memory expiry: empty (always, unless the quest is deliberately timed).

Greetings: "Mind the flour dust." and "You've the look of someone who's seen a donkey."

Patterns: keywords mill, flour → "I grind for three villages, when the wheel turns." — standing flavor, no quest logic.

Root text: "I can't talk long — my donkey's gone and the grain won't haul itself."
Root hints: "You could ask about the donkey."

Nodes, in this order:

NODE 1  id: offer-quest
  triggers:  donkey, help, quest, task        ← quest+task are REQUIRED
  text:   "Stubborn thing bolted toward the fen. Bring her back
           and I'll owe you real coin."
  hints:  "You could agree to find the donkey."
  quest gating:
    grantsQuest:   41-start
    questExcluded: 41-start, 41-end           ← BOTH tokens, always

NODE 2  id: fen-lore
  triggers:  fen, marsh
  text:   "The fen swallows carts whole. Keep to the reed line."

Why this order matters: node matching is substring-based and walks the list top-down. If fen-lore came first and a player asked about the "fen donkey", the lore line would shadow the quest offer. Quest-granting nodes always come first — the editor refuses the save otherwise.

Root variant (shown while the quest is active): text "Any sign of her? The fen's no place for a donkey overnight.", gated questRequired: 41-start, questExcluded: 41-end.

What the player sees in-game:

> talk hobb
Miller Hobb says, "I can't talk long — my donkey's gone and the
grain won't haul itself."
  [You could ask about the donkey.]
> ask hobb donkey
Miller Hobb says, "Stubborn thing bolted toward the fen. Bring her
back and I'll owe you real coin."
  [You could agree to find the donkey.]

The quest engine takes over from the grant: steps, completion, and rewards live in the quest YAML, not here. Dialogue's job ends at granting the token and reacting to quest state through gates.

5. Quest gating fields (the drawer)

FieldEffect
grantsQuestGives the player this quest token when the node/pattern fires.
questRequiredOnly fires if the player holds ALL listed tokens.
questExcludedNever fires if the player holds ANY listed token.
questFlagRequired / questFlagExcludedGate on quest flags — which branch of an opposed quest the player took.
setsQuestFlagRecords a branch choice (key + value must be declared in the quest YAML).
requiresItem / givesItemGate on, or hand over, a physical item.
givesGold / bumpsRep / masterworkRequiredCoin, reputation nudges, crafting-fame gate.
Prefer questRequired over node Requires for anything quest-critical: node memory can expire, quest tokens cannot. A grant node gated only by Requires draws a warning for exactly this reason.

6. What the editor refuses, and what it only warns about

Refused (the save does not happen)

  • grantsQuest without BOTH the granted token and its -end token in questExcluded — without the end token, a player who finished the quest gets it re-offered forever.
  • A quest-granting node missing quest and task triggers — breaks the universal ask <npc> quest gesture.
  • A quest-granting node listed after a non-granting node — ordering is matching priority; lore must never shadow a grant.
  • Semicolons in NPC text or hints — ; is the command separator and breaks the mob's say.
  • Unknown quest tokens, undeclared quest flags, nonexistent item ids, and Requires/Unlocks pointing at node ids that don't exist.

Warned (the save happens, the warning stays on screen)

  • An undiscoverable trigger — a trigger word that appears in no hint, no NPC text, and no root. If the player can't learn the word, the branch does not exist. (quest/task are exempt — they're the universal gesture.)
  • Memory expiry set — per-player dialogue memory that expires can strand mid-arc players. Only deliberate timed-quest designs want it.
  • A grant node gated by Requires instead of questRequired.

7. Voice rules

  • NPC text is spoken by the NPC — always first person ("I", "my mill").
  • Hints are the narrator addressing the player — "You could ask about the marriage", never "Ask her why she left" with a dangling "she".
  • No raw numbers in player-facing lines; keep lines under ~80 characters per sentence so MUD clients wrap them cleanly.
